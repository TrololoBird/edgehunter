# EdgeHunter — предложение по аудиту геометрии целей и препятствий (2026-10-26)

## Цель
Проверить, корректно ли система использует уровни рыночной структуры при построении торгового плана, не изменяя текущую торговую логику и не запуская контрфактический бэктест без отдельного разрешения.

## Исходные наблюдения (описательные)
За три дня (23–26.10.2026) — 168 входов с определённым типом TP1 (логи ENTRY, коммит 0dc59cb):
- 11 входов: TP1 только на источниках, которые в исследованиях проекта (research/level_weights.md) держали цену не лучше случайного уровня;
- 110 входов: TP1 связан со старшими зонами, веса которых (1.5–4.0) назначены вручную и не измерены;
- 47 входов: TP1 определён правилом метода.

По свечам Binance 1m:

| Группа | Входов | TP1 раньше стопа | Стоп раньше | Открыто |
|---|---|---|---|---|
| только «не лучше случайных» | 11 | 8 | 2 | 1 |
| старшие зоны с ручными весами | 110 | 52 | 34 | 24 |

В течение 4 часов после касания TP1:
- цена прошла дальше на 0.5R и больше: 6 из 8 и 28 из 52;
- цена вернулась на 1R и больше: 1 из 8 и 8 из 52.

Ограничения:
- для завершённых исходов первой группы знаменатель 10;
- «прошла дальше» и «вернулась» — не взаимоисключающие события, в одной сделке могут случиться оба;
- контрольной группы нет;
- выборки малы, сделки коррелированы.

Показатели не доказывают ни преимущества, ни вреда конкретного источника уровней.

## Проверки
1. **Разделить назначение уровней.** Для каждого источника определить, используется ли он как препятствие, ограничивающее ход; как цель фиксации; как ориентир структуры; как основание для отказа от входа по R:R (low_rr). Качество уровня для одной функции не переносить на остальные.
2. **Происхождение и независимость источников.** Восстановить исходные свечи, таймфрейм, время формирования и правило расчёта каждого уровня. Проверить, не считаются ли производные одного ценового события независимыми слагаемыми силы зоны.
3. **Система весов.** Сопоставить веса (config.py, LevelsConfig.weights) с обоснованием в коде, конфигурации и research/. Отдельно разобрать случаи, где несколько источников с весом 1.0 вместе превышают порог зоны min_strength 2.5. Отсутствие измеренного обоснования — методологический пробел, а не автоматически программный дефект.
4. **Варианты будущего изменения (без внедрения):**
   - A. Исключить слабые источники из формирования препятствий.
   - B. Снизить их вес либо применять разные веса для целей и препятствий.
   - C. Ограничить суммирование зависимых источников, построенных на одних и тех же свечах или экстремумах.

   Для каждого: ожидаемое изменение логики, риски, затрагиваемые стратегии, необходимые регрессионные тесты.

## Ограничения
- Не изменять код, конфигурацию и работающий демо-бот; текущие правила формирования целей не менять.
- Не запускать бэктест, контрфактический replay и подбор порогов.
- Не использовать постсигнальные признаки (ret_*, mfe_4h, mae_4h, outcome) для решений о входе.
- Не объявлять дефект подтверждённым без воспроизводимого расхождения со спецификацией.

## Требуемый результат
Отчёт, разделяющий:
1. подтверждённые дефекты реализации;
2. подтверждённые расхождения с документированной методикой;
3. методологические пробелы;
4. гипотезы, требующие исследования;
5. предложения по изменению геометрии с доказательствами и тестами.

Любое контрфактическое сравнение вариантов — только после отдельного согласования с владельцем.
