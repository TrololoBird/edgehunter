# План: качественное улучшение проекта за счёт ML (2026-10-02)

## 0. Исходная позиция (факты, не мнения)

- В проекте четыре модели:
  - `AnomalyModel`: IsolationForest, работает в тени;
  - `RegimeModel`: GaussianMixture, k=4;
  - `SuccessModel`: P(edge), онлайн-логистика river + ADWIN, работает в тени;
  - мета-модель в `research_meta.py` (LightGBM), не подключена к боту.
- Результаты на архиве:
  - P(edge) вне выборки: AUC 0.53, верхние ряды не лучше остальных;
  - мета-модель: AUC 0.63, но отобранные сделки всё равно −0.10R;
  - «грязный» R карточек ≈ 0, убыток равен издержкам (~0.20% за круг).
- Вывод: **у первичных сигналов нет края, поэтому ML-фильтр не может его создать**. Модель, которая выбирает
  из сделок с нулевым ожиданием, выбирает шум. Значит, ML полезен в трёх местах:
  1. там, где задача реально предсказуема: волатильность, издержки, вероятности барьеров, режимы;
  2. как строгий судья, который не даёт принять шум за край;
  3. как поиск края на данных, которых нет в архиве: запись стакана, ликвидации, другие биржи.
- Ограничения:
  - ручной вход на 1h–4h, опоздание на секунды;
  - издержки ~20 bp за круг;
  - ноутбук на 6 ГБ RAM, модели работают только в отдельном процессе;
  - бот на Windows, облако только для архивной работы;
  - правило владельца: сигнальная логика замораживается на 7 дней после смены версии.

## 1. Принципы (действуют для каждого пункта ниже)

1. **Предрегистрация.** Цель, метка, признаки, метрика, порог «принять» и порог «убить» записываются в
   `research/prereg/<id>.md` до первого прогона. Менять их после прогона нельзя.
2. **Реестр попыток.** Каждый вариант (модель × признаки × гиперпараметры × метка) — строка в
   `research/trials.csv`. Из этого числа считаются deflated Sharpe и PBO.
3. **Тройное разбиение по времени.** Развитие → валидация (CPCV) → запертая отложенная выборка, на которую
   смотрят один раз. Сейчас отложенная выборка — 2026-04-01 … 2026-09-30.
4. **Метка за вычетом издержек**, против среднего по вселенной (не медианы, см. eng-7), с учётом
   фандинга и проскальзывания по ликвидности.
5. **Плацебо и нулевой мир.** Каждый конвейер прогоняется на синтетических данных без предсказуемости
   (перемешанные блоки доходностей с сохранением волатильности). Если конвейер там что-то «находит»,
   он сломан.
6. **Совпадение признаков в обучении и в работе.** Признак в архиве и в живом журнале должен считаться
   одним и тем же кодом. Тест: те же монета и время в `pretrain_rows` и в `signals.db` дают те же значения.
7. **Тень → вес → решение.** Новая модель сначала только журналируется (≥ 30 независимых 4h-кластеров),
   потом показывается на карточке, и только после этого может что-то фильтровать.
8. **Простой эталон обязателен.** HAR против LightGBM, геометрия случайного блуждания против
   классификатора, ATR14 против прогноза. Сложная модель принимается только если бьёт эталон вне выборки
   по тесту Диболда–Мариано или бутстрэпу.
9. **Одно изменение за раз** в живой логике, со сменой `logic_version`.

## 2. Фазы

### Фаза A. Фундамент оценки (без неё всё остальное недостоверно)
Цель: любой результат проходит одну и ту же строгую проверку.

- A1. Модуль `validation.py` (общий для `stats.py`, `ml_eval.py`, `research_*.py`):
  - CPCV (combinatorial purged CV) с purging по окну метки и embargo;
  - deflated Sharpe ratio (Bailey, López de Prado) с числом попыток из реестра;
  - PBO (probability of backtest overfitting) по матрице «вариант × разбиение»;
  - блочный бутстрэп по 4h × направление (уже есть в `research_edges.block_stats`, перенести);
  - Benjamini–Hochberg (уже есть, перенести).
- A2. `research/trials.csv` с полями: дата, скрипт, стратегия / модель, параметры, окно, метрика dev /
  валидация / отложенная выборка, хэш данных, коммит. Задним числом занести попытки из навыка
  research-findings (оценочно десятки).
- A3. Аудит нулевого мира (`null_audit.py`): синтетические 1m-свечи из блочного перемешивания реальных
  доходностей с той же волатильностью. Через полный конвейер пропустить `research_cards`,
  `research_maniac`, `research_classic`, `pretrain → ml_eval`. Ожидаемый результат — Edge ≈ −издержки,
  AUC ≈ 0.5. Любое отклонение означает утечку.
- A4. Тест совпадения признаков: 200 случайных живых строк журнала против строк, пересчитанных
  `pretrain.py` по архиву на те же минуты. Допуск по каждому признаку; признаки вне допуска помечаются
  `live_only`.
- A5. `ml_eval.py`: перейти с одного walk-forward на CPCV и выдавать распределение AUC, log-loss и Edge
  верхнего дециля, плюс PBO.
- Готово, когда нулевой мир даёт ноль, а реестр и DSR / PBO печатаются в `stats.py` и `ml_eval.py`.

### Фаза B. Модели риска (самый высокий шанс на пользу)
Цель: стоп, размер позиции и проверка «окупит ли цель издержки» опираются на прогноз, а не на ATR14.
Источник: волатильность хорошо прогнозируема (HAR-RV, бустинг), направление — нет.

- B1. **Прогноз реализованной волатильности** на 1h и 4h вперёд, на каждую монету.
  - Эталоны: ATR14 (сейчас), max(ATR14, ATR последнего часа) (сейчас), HAR-RV (дневной / часовой /
    15-минутный RV).
  - Кандидат: LightGBM с признаками HAR-лагов, сезонности (час, выходные; уже есть
    `seasonal_factors`), RV BTC и рынка, объёма, OI, фандинга, расстояния до 24h-экстремумов.
  - Метрика: QLIKE и MSE log-RV вне выборки, тест Диболда–Мариано.
  - Данные: архив 1m за 18 месяцев, все монеты (уже качаются).
  - Принять, если QLIKE лучше HAR на ≥ 5% в обеих частях и DM p < 0.05.
- B2. **Вероятность «цель раньше стопа»** для любой пары уровней: геометрия случайного блуждания с
  прогнозной волатильностью и дрейфом, равным нулю. Сейчас в `scenarios.py` геометрия уже почти
  идеально откалибрована. Проверка: заменить волатильность на прогноз из B1 и посмотреть, улучшается ли
  калибровка на коротких горизонтах (Brier). Новый классификатор не нужен.
- B3. **Модель проскальзывания и издержек** по записанному стакану (`recorder.py`, глубина по полосам
  0.1%): ожидаемое проскальзывание рыночного входа и стоп-выхода на размер позиции. Сейчас там формула
  «5 bp × √($500M / объём)», а на гипотезы её никто не проверял. Метрика — ошибка против фактических
  исполнений демо BingX (`demo_trades.db`).
- B4. **Прогноз фандинга** на время удержания: HAR / AR по истории фандинга + премия. Сейчас за всё
  удержание берётся ставка в момент сигнала (`levels.funding_r`).
- B5. **Встроить в план сделки** (после принятия B1–B3, отдельная версия логики):
  - нижняя граница стопа = k × прогноз волатильности на горизонте сделки (сейчас `min_stop_atr` × ATR);
  - проверка R:R с прогнозными издержками;
  - размер позиции по прогнозу волатильности (уже есть `webui.sizing_view`, сейчас по стопу).
  - Проверка: прогон карточек `research_cards` на отложенной выборке со старой и новой геометрией.
    Ожидание скромное: архив показал, что геометрия выхода не создаёт край. Польза — меньше случайных
    выбиваний и меньше сделок, которые не могут окупиться.
- Готово, когда B1 принят или убит, B2 / B3 измерены, а решение по B5 записано.

### Фаза C. Режимы рынка
Цель: устойчивый и интерпретируемый контекст. Сейчас у GaussianMixture было 8 имён на 4 кластера.

- C1. Заменить `RegimeModel` на HMM с «липкими» переходами (hmmlearn или собственная реализация,
  диагональная ковариация). Признаки те же: движение и волатильность BTC за 1h, широта рынка,
  медианы фандинга, OI и RVOL. Плюс недельный тренд (`trend_w`, `breadth_w`).
- C2. Стабильные имена: после переобучения состояния сопоставляются с прошлыми по центрам
  (венгерский алгоритм), а имя закрепляется за состоянием.
- C3. Оценка:
  - устойчивость: средняя длительность режима и число смен в сутки против GMM;
  - полезность: Edge стратегий по режимам, уже с FDR-контролем (`journal.proven_negative`).
- Принять, если режимы устойчивее, а разбиение стратегий по ним не хуже. Края от этого не ждём:
  режимы — это контекст, а не триггер.

### Фаза D. Аномалии (Tier-0)
Цель: понять, нужен ли IsolationForest вообще.

- D1. Измерить, что происходит после аномалии: доходность и волатильность через 15m / 1h / 4h после
  срабатываний правил против IsolationForest против случайных минут той же монеты. Данные — журнал
  (столбцы `t0_*`, `ml_score`) и архив (правила воспроизводятся в `pretrain.py`).
- D2. Если IsolationForest не лучше правил по связи с будущей волатильностью — выключить и удалить его
  процесс-воркер: это минус RAM на ноутбуке. Если лучше — заменить пороги правил на условные квантили
  по монете и часу (robust z), а не оставлять две системы рядом.
- Готово, когда одна из двух систем удалена.

### Фаза E. Фильтры существующих сигналов (мета-разметка 2.0)
Разрешено **только** для стратегий, у которых на архиве или в журнале «грязный» R > издержек хотя бы
в одной части. Иначе фильтру нечего выбирать.

- E1. Список кандидатов — по итогам текущего прогона (`research/validation_eng43.md`).
- E2. Метка: triple-barrier (стоп / TP1 / время жизни сделки) за вычетом издержек. Признаки — только
  известные на момент входа, плюс прогнозы из B1 / B4 и режим из C1.
- E3. Модели: логистика (эталон) → LightGBM с монотонными ограничениями там, где знак известен
  (например, издержки / риск). Калибровка изотонической регрессией на отдельном куске. Порог входа —
  ожидаемый R > 0 с учётом издержек, не p > 0.5.
- E4. Оценка: CPCV + PBO + отложенная выборка; сравнение R отобранных сделок с R всех сделок той же
  стратегии и с плацебо-выбором того же числа сделок.
- Убить, если PBO > 0.5 или на отложенной выборке R отобранных ≤ R всех.

### Фаза F. Данные, которых нет в архиве (единственный честный источник нового края)
Цель: проверить микроструктуру как фильтр для сделок на 1h–4h. Для этого и записывается `recorder.py`.

- F1. Накопить данные: ≥ 60 дней записи (поток по секундам × биржа, полосы стакана, OI / фандинг
  поминутно), проверить пропуски и время.
- F2. Признаки:
  - дисбаланс потока на границе 15 минут: эффект на 4–12h задокументирован на фьючерсах Binance
    (arXiv 2607.09426, 5–17 bp — **меньше издержек**, значит только как фильтр);
  - доля одной биржи;
  - ликвидации по сторонам;
  - дисбаланс полос стакана и устойчивые полосы ликвидности;
  - спот против фьючерса по всем биржам;
  - премия Coinbase;
  - чистая позиция крупных аккаунтов Hyperliquid.
- F3. Сначала простая статистика без ML: условная доходность и волатильность на 1h / 4h по децилям
  признака против среднего по вселенной, блочный бутстрэп, FDR по всем признакам × горизонтам.
- F4. ML (как в E) — только для признаков, прошедших F3.
- F5. Вклад в P(edge): живые признаки добавляются в `SuccessModel` с флагом наличия (в архиве их нет).
  Проверка — CPCV на живом журнале.

### Фаза G. Одна предрегистрированная проверка кросс-секционного ранжирования
Литература: в крипте альфа ML сидит в неликвидных монетах (Cakici и др., 2024). Наша вселенная —
ликвидная, а простой XSMOM на архиве не повторился. Ожидание — провал. Проверка дешёвая, данные есть.

- G1. LightGBM ranker (lambdarank) по монетам вселенной на 4h и 24h вперёд против среднего по
  вселенной. Признаки: моментум 1h / 4h / 1d / 7d, волатильность, неликвидность (Amihud), фандинг,
  OI, бета к BTC.
- G2. Эталоны: равные веса и простой моментум. Издержки по `levels.slippage_bps`.
- G3. Одна попытка, одна отложенная выборка. Не прошло — тема закрыта и записана в research-findings.

### Фаза H. Эксплуатация моделей (MLOps на ноутбуке)
- H1. Карточка модели рядом с каждым файлом: `models/<name>.json` с окном данных, `logic_version`,
  хэшем признаков, метриками вне выборки, датой и коммитом. Бот не загружает модель без карточки или с
  чужой `logic_version` (для P(edge) уже так).
- H2. Мониторинг дрейфа: PSI по каждому входному признаку против окна обучения (раз в час, в
  Health-строку и вкладку здоровья). ADWIN по ошибке уже есть в `SuccessModel`.
- H3. Автоматический откат на прошлую модель, если ошибка вне выборки за 7 дней хуже эталона.
- H4. Ресурсы: все модели в процессе-воркере (уже так для IsolationForest и карт). Бюджет RAM на модели
  ≤ 300 МБ. LightGBM-модели сохранять в текстовом формате booster, без pickle.
- H5. Переобучение по расписанию:
  - объединить `pretrain_loop`, обучение волатильности и режимов в один ночной запуск с низким
    приоритетом;
  - облачная сессия — для тяжёлых архивных прогонов.
- H6. Воспроизводимость: фиксированные зёрна, версия данных (список файлов архива + хэш), окружение
  (`requirements.txt` с точными версиями для исследований).

## 3. Чего не делать (и почему)
- **Модели стакана на секунды** (DeepLOB, TLOB, LiT). Горизонт — секунды, вход ручной, результаты в
  статьях без учёта задержки и почти без издержек.
- **Готовые нейросети для временных рядов** (Chronos, TimesFM, Moirai). Без дообучения прогнозы не дают
  экономически значимой стратегии (Rahimikia и др.); точность направления ~51.7% — меньше издержек.
- **Обучение с подкреплением на исполнение и торговлю.** Нет симулятора с реалистичным влиянием на цену;
  переобучение гарантировано при нашем объёме данных.
- **LLM-сигналы и сентимент.** Нет архива с точными метками времени, высокий риск заглядывания вперёд.
- **Подбор порогов детекторов оптимизатором** (Optuna и т. п.) без реестра попыток и PBO. Это ровно
  механизм ложных открытий.

## 6. Как понять, что план сработал
- **Минимум (почти наверняка достижимо):** проект перестаёт принимать шум за край — нулевой мир даёт
  ноль, у каждого вывода есть DSR / PBO, а число попыток учтено.
- **Вероятно достижимо:** стопы и размер позиции по прогнозу волатильности, который бьёт ATR14 и HAR;
  меньше сделок, которые заведомо не окупают издержки.
- **Неизвестно (честный шанс, а не обещание):** край от микроструктурных данных из recorder как
  фильтр для 1h–4h. Литература показывает эффекты в несколько bp, то есть меньше издержек.
- Ни один пункт не гарантирует прибыльную стратегию. Это план по улучшению качества решений и по
  измерению, а не по обещанию дохода.
